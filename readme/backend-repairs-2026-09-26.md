## 验证方式

最终结果：`npm test` 共 **132 项通过，0 项失败**（31 + 25 + 76）。主 Worker、state-gateway 打包与隔离 Node 启动检查通过。独立复查已核验目录批量遍历、分片竞争和 multipart 恢复记录的后续修复。

- `npm test`：原有测试及全部新增后端回归测试。
- `node test/node-runtime-smoke.mjs`：独立临时数据库启动 Node，验证迁移、静态资源、路由及中间件，不读取工作区业务数据。
- `node --import ./deploy/server/register.mjs test/backend-performance.mjs`：独立临时目录读写 256 MiB 对象，采样进程内存与事件循环延迟。
- `npx wrangler deploy --dry-run --config deploy/worker/wrangler.toml --outdir .codex-tmp/backend-worker-build`：仅本地 Worker 打包，不部署。
- D1 SQL 与导出预算还经过 Miniflare/workerd 验证；数据库导出快照经过双连接并发写入验证。

本机 Node v24.11.1 的一次 256 MiB 流式写入/读回：写入 789 ms，总计 2086 ms，RSS 峰值相对启动增加约 49 MiB，事件循环 P99 约 13 ms。该数据不是线上压测，也没有与旧版本做同环境吞吐对比。

10 万条元数据的分页回归验证了：请求 50 条时只物化 51 条文件元数据（多一条用于判断下一页）；SQL 计数和随机选择仍可能在数据库内部扫描候选行。

## 升级与运行边界

1. D1/SQLite 新增 `files.expires_at`、`settings.expires_at` 及查询索引。适配器使用前会检查并兼容升级；显式迁移文件位于 `database/migrations/v2.7.7_01_*` 至 `v2.7.7_03_*`。已有列时不要重复执行对应 ALTER；Node 启动迁移会忽略已存在列。
2. Worker cron、Node 每分钟定时器和授权的外部备份 runner 都执行维护。每次处理最多 100 条过期记录、100 条别名回填、20 条 multipart 恢复记录、20 条分片处理权记录及有限页容量核对。旧数据公开别名在回填到对应记录后可用；旧版已遗失的 TTL 无法自动推算；无法确定存储服务或过期时间的历史 multipart 记录会保留，避免丢失恢复标识。
3. 容量账本保守计费，删除及外部写入通过后台核对反映。首次和更改配额需要建立全桶基线；核对过程中可能暂时多计容量，避免少计进行中的上传。绕过应用直接写存储不受请求侧配额控制。
4. 普通上传实际请求体上限为 100 MiB，分片 16 MiB（另有有限表单开销）；DAV PUT 上限 100 MiB。大文件应使用分片。不可取消的 R2 RPC 超时后会等待其结束，避免返回后继续写入。
5. 图片默认同时处理 1 个、最多排队 8 个；通过 `IMAGE_TRANSFORM_MAX_ACTIVE`、`IMAGE_TRANSFORM_MAX_QUEUED` 调整。`IMAGE_TRANSFORM_CONCURRENCY` 仍表示每个 sharp 任务的内部线程数。
6. 内联数据库 JSON 导出上限为 10000 行、保守估计 16 MiB；更大的库需使用原生 D1 导出完整快照，不能把 413 当作备份成功。
7. 纯 KV 仍不具备分布式 CAS。并发分片处理要求 R2 或 D1 提供持久化处理权；当前项目已配置两者。KV 普通单文件上传保留。KV 索引和显式批量重建/导出仍会加载整份快照，不能据此宣称所有批量操作内存恒定。
8. 没有使用真实 Telegram、Discord、S3 或线上 Cloudflare 数据做压力测试。上线后的混合并发负载、容器内存峰值和服务侧限额仍需观测。
